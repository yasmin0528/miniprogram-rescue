# 派单分享功能设计方案

## 1. 业务场景描述
- **角色**：服务商（派单者）、师傅（接单者）。
- **流程**：
    1. 服务商在“订单大厅”抢单成功。
    2. 服务商在“我的订单”中点击“派单”按钮，通过微信分享链接给师傅。
    3. 师傅点击链接进入小程序，系统自动识别参数并确认接单。
    4. 师傅完成服务，在订单详情页点击“完成订单”。
    5. 系统自动结算，更新状态，派单者与师傅同步看到订单已完成。

## 2. 分享链接协议设计
分享路径：`/pages/orders/detail` (或专门的接单落地页)
参数定义：
- `id`: 订单 ID
- `sharer`: 派单者用户 ID
- `amount`: 订单总金额（用于展示）
- `commission`: 师傅可获得的金额/抽成比例（由派单者设定或系统计算）
- `from`: 固定值 `dispatch` (用于标记来源)

**示例 URL**:
`/pages/orders/detail?id=123&sharer=456&amount=100&commission=80&from=dispatch`

## 3. 核心流程实现

### A. 派单发起逻辑 (服务商端)
在 `pages/orders/orders.uvue` 中实现：
- 监听“派单”按钮点击。
- 调用微信分享 API (`onShareAppMessage`)。
- 动态构造带参数的 `path`。

### B. 接单确认逻辑 (师傅端落地页)
在订单详情页的 `onLoad` 或 `onShow` 中：
1. **参数解析**：提取 `id`, `sharer`, `commission` 等。
2. **状态校验**：
   - 检查当前用户是否为师傅角色。
   - 调用后端接口查询订单状态，确保该订单尚未被其他人接取。
3. **自动/手动确认**：
   - 弹出确认框：“您收到来自 [派单者] 的订单，金额为 [commission]，是否接受？”。
   - 师傅点击确定后，调用后端 `acceptDispatch` 接口。

### C. 订单执行与状态同步
- **状态流转**：
  `已抢单` -> `派发中` -> `师傅已接单` -> `服务中` -> `已完成`。
- **完成动作**：
  师傅点击“完成订单” -> 调用 `completeOrder` 接口。
- **通知机制**：
  后端处理逻辑中，在 `completeOrder` 被调用时，需同时更新派单者和师傅的订单视图。

### D.建议在订单详情页增加一个 [转派申请] 功能。
- 逻辑流程设计：
- 师傅端动作：点击 [转派申请] -> 填写原因（如：需要大吊车/工具不足）-> 提交。
- 服务商端通知：服务商收到推送或在列表看到“待转派”状态。
- 服务商端操作：点击 [同意转派并重新派单]。此时系统自动执行“撤回”动作，并直接打开金额设置界面。

## 4. 接口需求定义 (后端)
1. **`POST /api/order/dispatch`**: 记录派单动作，设置订单为派发中状态。
2. **`POST /api/order/accept`**: 师傅接单，绑定订单与师傅的关系。
3. **`POST /api/order/complete`**: 完成订单，触发佣金结算逻辑。

## 6. 角色权限与视图差异

| 功能模块 | 服务商 (派单者) | 师傅 (接单者) |
| :--- | :--- | :--- |
| **订单金额** | 显示总额 + 抽成设置 | 仅显示接单可得佣金 |
| **派单操作** | 可发起分享、可撤回 | 无权发起分享/撤回 |
| **订单反馈** | 仅查看师傅上传的内容 | 需上传现场照片并点击完成 |
| **异常处理** | 同意/拒绝转派申请 | 发起转派申请 (无法处理时) |

## 7. 协作转派方案 (Expert Solution)
针对“师傅抵达现场无法解决”的场景，采用“服务商主导，师傅申请”的模式：

1. **发起申请**：师傅在订单详情页点击 [申请转派]，填写原因（如：工具不匹配）。
2. **状态通知**：订单状态变更为 `TRANSFER_PENDING` (转派待定)，并向服务商推送通知。
3. **服务商决策**：
   - **同意**：点击 [同意转派]，系统执行 `revokeDispatch` 逻辑。订单回归服务商“待处理”池，服务商可立即重新设置金额并分享给新师傅。
   - **拒绝**：要求原师傅继续完成或按其他协议处理。
4. **优点**：确保了资金结算的单一性（服务商 -> 最终干活的师傅），避免了师傅间私下转账产生的纠纷。

## 9. 数据所有权与双重身份判定逻辑

系统中通过以下字段动态判定用户在当前订单中的角色：

1. **服务商身份 (Owner/Provider)**: 当 `current_user_id == order.provider_id`。
   - 权限：拥有 [撤回]、[管理抽成]、[确认转派] 权限。
   - 视图：可见订单总额及分配给师傅的抽成比例。
2. **师傅身份 (Worker/Master)**: 当 `current_user_id == order.master_id`。
   - 权限：拥有 [完成订单]、[发起转派申请] 权限。
   - 视图：仅可见自己应得的佣金。

## 10. 转派消失逻辑与重派流程

1. **师傅申请转派**: 
   - 师傅点击 [申请转派] 并确认。
   - 接口调用成功后，前端立即将该订单从师傅的 `orders` 列表中剔除。
   - 后端重置订单的 `master_id` 为空，状态变更为 `WAITING_DISPATCH`。
2. **服务商重发**: 
   - 服务商在列表/详情中看到转派申请。
   - 点击 [同意并重派]：实际上是触发一个新的 `setCommissionAndShare` 流程。
   - 服务商根据实际情况重新输入抽成金额，生成新的分享链接。
